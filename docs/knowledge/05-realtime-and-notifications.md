# Tripinly — Real Time and Notifications

## Real time (Socket.IO)

- Namespace `/v1/realtime` (Socket.IO default path `/socket.io`, WebSocket transport). Clients connect with the access token in the handshake `auth.token`. A refused handshake arrives as `connect_error` with `data.code`: `UNAUTHENTICATED`, `TOKEN_EXPIRED`, `ACCOUNT_SUSPENDED`, `ONBOARDING_INCOMPLETE` or `CONSENT_REQUIRED` (the same gate as REST). When the token expires on an open socket, the server emits `error { code: "TOKEN_EXPIRED" }` and disconnects; the client refreshes, reconnects and refetches.
- Redis adapter so several API instances share rooms. The worker publishes through the same Redis (`@socket.io/redis-emitter`), so events raised there (photo processing, notifications) reach sockets too.
- Rooms:
  - `user:{userId}` — joined automatically on connect. Personal notifications, trip list changes.
  - `trip:{tripId}` — joined via `trip.subscribe { tripId }`. The server runs the `TripAccessService` read check before joining; leave with `trip.unsubscribe { tripId }`. Both answer through the Socket.IO acknowledgement: `{ ok: true, tripId }` or `{ ok: false, tripId, error: { code } }` (`NOT_FOUND` without access, `VALIDATION_FAILED` for a bad id); a refusal is also emitted as `error { code, tripId }`.
- **Open views** (added 2026-11-07): a socket that joined `trip:{tripId}` has that trip's map open. `comments.watch { markerId }` says a stop's comments are open (read check first; ack `{ ok, markerId }` or `{ ok: false, markerId, error }`), `comments.unwatch { markerId }` closes them. The gateway keeps open views in Redis per user (`viewing:{userId}:{view}`, the socket ids holding it, forgotten after an hour without a new open), and drops a socket's views when it disconnects. The worker skips a push while its view is open on any of the recipient's devices: news about a stop's comments while those comments are open, a collaborator's change while that trip's map is open. The row, the live event and the red dot stay. The apps leave rooms when they go to the background, so pushes resume there.
- Sockets that lose `view` are removed from the room: non-members when the trip turns private, a removed member of a private trip (or after a block), each side of a new block from the other's trips. `trip.deleted` is sent, then the room is emptied.
- Events are **notifications of change with enough data to update the UI**, not a replacement for REST. On reconnect, clients refetch the trip.
- Every event payload: `{ "event": "...", "tripId": "...", "actorId": "...", "at": "ISO", "data": { ... } }`.
- The actor's own socket also receives events (clients de-duplicate by entity ID).
- Blocked users are never delivered events caused by the user they blocked (or who blocked them).
- Payloads are the REST DTOs, made viewer-neutral: `likedByMe` (`hotByMe` on markers) is always `false` in marker, photo and comment payloads (and `canDelete` false on comments); keep the local value.

Silent on purpose: unfollows, leaving a trip, a deleted trip, copies, deleted photos, covers, unlikes, flames on OSM spots, blocks and lost access. Single flames and likes between milestones show only in the notification center (Shahin, 2026-11-01 and 2026-11-07: pushes cost money; a famous spot can sit in hundreds of trips).

**Notification center (2026-11-07):** every entry above shows in the app's center (`GET /v1/notifications`, newest first). `unseenCount` counts entries new or moved back on top since the user last opened it (`POST /v1/notifications/seen`, stored in `users.notificationsSeenAt`); it drives the red indicator on the Profile tab and the center tab. Seen is not read: stop marks clear only by `POST /notifications/read`. Read is seen: an entry read anywhere stops counting as unseen, so seeing a comment on the map also clears the bell when nothing else waits (2026-11-07). Removing notifications (`DELETE /notifications/{id}`, `DELETE /notifications`) deletes only the notification rows; account deletion deletes the user's own rows and takes them out of other people's groups (the next person becomes the actor).

**Grouping (2026-11-07, Shahin's choices):** the worker groups at write time, so the app gets ready-made rows and groups nothing itself. A new notification with a group key joins the **open** row of that key (one not read yet: a group stops growing when it is tapped; opening the center only clears the red indicator) and moves it back on top, unread, with `count` + 1 and the person at the front of `payload.actorIds` (latest first, unique). Without an open row it starts a new one. Keys, per recipient:

| What                            | Key                                        | Row reads                                              |
| ------------------------------- | ------------------------------------------ | ------------------------------------------------------ |
| Comments on a stop              | `comments:{markerId}:{me}`                 | Anna commented 3 times / Anna and Jonas commented on X |
| Replies to a main comment       | `replies:{commentId}:{me}`                 | Anna and 2 others replied on X                         |
| Collaborator changes            | `changes:{tripId}:{markerId or trip}:{me}` | Changes in Vienna / Anna made 3 changes                |
| Likes, flames                   | per item, as before                        | Anna and 4 others liked your photo                     |
| Saves                           | `saves:{tripId}:{me}`                      | Mia and 3 others saved your trip                       |
| Follows                         | `follows:{me}`                             | Mia and Leo followed you                               |
| Mentions, friends, trip notices | never grouped                              | one row each                                           |

Changes group per stop so a stop's "new" dot still clears on its own. Pushes don't change: they follow the table above per event (milestones read from the key's latest row, so a new row never pushes a milestone twice). Deleting a comment takes it out of its group (count, people and excerpt recomputed; the row goes when it was the last). The API returns up to 3 people as `actors` (latest first). Migration `notification_groups` drops the one-open-row-per-key index.

- The API turns domain events into `plan` jobs on the `notifications` queue; the worker picks recipients, writes rows and sends. Recipients never include the actor, anyone with a block either way with the actor, inactive accounts, or anyone who can't view the trip.
- **Every notification pushes at once** (Shahin, 2026-11-01; replaces the 10-minute batch and the hourly likes summary). The same notification again (same recipient, same person, same kind, same item: a like, unlike and like again; the same stop moved twice) within `NOTIFICATION_REPEAT_COOLDOWN_SECONDS` (worker, default 5) is dropped, row and push.
- Collaborator changes are: trip updated, day added/deleted, marker added/updated/deleted, markers reordered, photo uploaded.
- Own likes never notify. Hot marks only count toward `place_hot` milestones. Likes on a trip go to its owner, on a photo to its uploader, on a comment to its author. Stops have no likes of their own (their place does).
- At send time the recipient's access is checked again: someone who lost access to the trip gets no push and the entry is deleted. The in-app list also hides entries about trips the user can no longer see, and entries caused by someone they have a block with. Deleting a comment deletes its notifications (a main comment's replies and theirs too).
- Respect `notification-settings`: each switch turns off its whole group (column Switch above; `SETTING_FOR_TYPE`). The in-app notification is still created when the push is off, so pin marks still show.
- **New-activity marks:** `GET /v1/trips/{id}/new-activity` returns the stops of the trip with unread notifications for me (same visibility as the list: no blocked actors). The app shows them as "new" dots on pins and day tabs; `commentMarkerIds` says which of them have unread news about their comments (a new comment or a like on one; `aboutComments` on each notification). Opening a stop sends `POST /v1/notifications/read` with `{ markerId, kind: "other" }`, clearing the rest; opening its comments sends `kind: "comments"`. A mark goes once both are read (`{ markerId }` alone still reads everything). A `notification.created` with a `markerId` adds a mark live (2026-11-05).
- Localize using the recipient's device `locale` (fallback user locale, then `en`). Templates live in the i18n files, keyed `push.<type>.title` / `.body` with ICU plural support.
- Payload: a `notification` (title, body) plus `data: { type, notificationId, deepLink }`. Deep links: `tripinly://markers/{id}/comments` (comments, replies, mentions and comment likes: the stop's comments sheet; added 2026-11-07), `tripinly://markers/{id}` (anything else about one stop; older apps open its trip), `tripinly://me/followers` (a group of several followers; added 2026-11-07), `tripinly://trips/{id}/members` (join requests), `tripinly://users/{username}` (follows), `tripinly://trips/{id}` (everything else about one trip), `tripinly://notifications` (nothing to open, e.g. an old grouped summary or a hot spot with no stop of the creator's).
- Pushes are skipped while `FIREBASE_SERVICE_ACCOUNT_JSON` is unset; in-app notifications and realtime still work.
- Remove device tokens that FCM reports as unregistered.
- Never include private trip content in a push to someone who isn't a member.

## Email

Transactional only, via Resend, localized templates:

| Email                        | When                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------ |
| `data_export_ready`          | Export job finished; contains a signed download link valid 7 days                                      |
| `account_deletion_confirmed` | Deletion finished (sent to the provider email captured before deletion, then the address is discarded) |

No marketing email in v1.

- Queued with `EmailService.send(template, to, locale, params)` on the `email` queue; the worker renders (`i18n/<lang>/email.json`, HTML plus a text part) and sends through Resend with the job id as idempotency key. Five attempts with backoff.
- The address exists only in the job, which is removed when it finishes or fails; logs name the template, never the address.
- Skipped with a warning while `RESEND_API_KEY` is unset. `EMAIL_FROM` must be an address on a domain verified in Resend.
